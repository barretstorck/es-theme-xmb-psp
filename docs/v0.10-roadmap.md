# v0.10 Planned Features

Roadmap for features deferred from v0.9.3 — each needs a proper brainstorm + design pass before implementation. ES feature-feasibility research from v0.9.3 round 4 is summarized inline so we don't have to rediscover the same constraints.

---

## 1. Adaptive layout based on game metadata

**What the user wants:** When a game has no description, the image/video expands into that space. When a game has no image/video, the description expands. Empty slots shouldn't leave empty space.

**ES support status:** **Partial.**

- `<visible>exists({game:image})</visible>` and similar bindings work — we can HIDE empty elements.
- `<pos>` and `<size>` are NOT bindable to expressions — we cannot REFLOW remaining elements.

**Possible approaches:**

1. **Hide-only (cheap, partial fix):** Add `<visible>` bindings on `md_video`, `md_description`, `md_image`, etc. Empty elements disappear; remaining elements stay in their original positions. User sees blank space where the hidden element was — better than the current "rendering of empty container" but not the full reflow.
2. **Multiple view variants:** Ship 3–4 explicit `gamelist` layout variants (e.g., `detailed-full`, `detailed-no-video`, `detailed-text-only`) and let the user pick via a theme subset. Honest but rigid — doesn't auto-adapt per game.
3. **Per-game storyboards:** Use binding-driven storyboards to animate elements into different positions based on metadata presence. Probably not supported, but worth a research spike.

**Open questions for brainstorming:**

- Is "blank space" acceptable for the hide-only approach? (probably ugly)
- How many view variants is sane before it's too many? (4 max?)
- Does the storyboard approach work for non-time-based triggers like metadata bindings?

**Evidence:** `THEMES_BINDINGS.md:264-302`, `THEMES.md:1398`, `ThemeData.cpp:1083`

## 2. Per-logo titles under every gamecarousel boxart

**What the user wants:** Every boxart in the vertical gamecarousel has its game title rendered directly below it, not just the selected one.

**ES support status:** **Not directly supported.**

- The `gamecarouselLogoText` element is only rendered as a FALLBACK when a game has no thumbnail (image fallback → text).
- The carousel doesn't natively support a per-logo text overlay rendered alongside an image.

**Possible approaches:**

1. **`<itemTemplate>` system:** ES supports `<itemTemplate>` inside `<gamecarousel>` for custom per-item layouts. Complex; needs research on how component bindings work within templates.
2. **Overlaid title at fixed position:** Position a separate `<text>` element at the carousel container's center, bound to `{game:name}` — but this only shows the SELECTED game's title, not per-logo titles.
3. **Accept the limitation:** Match what PSP XMB actually does (which is selected-game label only on PSP's video item carousel).

**Open questions for brainstorming:**

- Is XMB-faithful behaviour (selected-only label) actually OK with the user, or do they specifically want per-logo?
- If per-logo is the goal, does `<itemTemplate>` actually work in this ES build? Needs a feasibility spike.

**Evidence:** `CarouselComponent.cpp:748-767`

## 3. Selected-game halo in the gamecarousel

**What the user wanted:** A halo behind the selected boxart in the gamecarousel, matching the system carousel's selected-icon halo.

**Why it's deferred:** v0.9.3 round 4 implemented this naively (`<image name="selectedGameHalo">` with the same `art/halo.png`). On-device test revealed that when a game has no thumbnail and the carousel falls back to text rendering, the white halo makes the title text unreadable.

**Possible approaches:**

1. **Conditional halo visibility:** Only show the halo when the selected game has a thumbnail: `<visible>exists({game:thumbnail})</visible>`. Halo behind images, no halo behind text. Requires verifying `exists()` binding works correctly on the halo element.
2. **Different halo design for gamecarousel:** Use a more subtle halo (e.g., a colored rectangle frame, or a lower-opacity glow) that doesn't obscure text. Different from the system halo design.
3. **Move the halo above text in zIndex:** Put text fallback at a higher zIndex than the halo. May still look bad if the halo's bright peak is behind the text.
4. **Couple with item 5 below** (per-system fallback icons) — if games without thumbnails show a system media icon instead of text, the halo wouldn't conflict with text readability.

**Open questions for brainstorming:**

- Pick approach 1 (conditional visibility) or approach 4 (couple with fallback icons) as the path?
- Is the design intent "halo per game" or "halo for the carousel selection slot"?

**Evidence:** v0.9.3 round 4 commit history; on-device user feedback.

## 4. Halo fade on carousel scroll

**What the user wants:** When the system carousel is transitioning between systems, the halo fades out (so it doesn't look like a stuck static dot during scroll); after the transition completes, the halo fades back in.

**Status:** **Partially shipped in v0.9.3 round 4 — verification pending.**

- Added `<storyboard event="scroll">` to `_inc/system.xml`'s `selectedHalo`:
  - On scroll-event: opacity 1 → 0 in 120 ms (linear)
  - Default (no-event) storyboard: opacity 0 → 1 in 220 ms (linear)
- The mechanism is theoretically correct per `CarouselComponent.cpp` research (the carousel emits a `"scroll"` event on cursor change). Whether it reaches a `screen`-view extra element rather than only a carousel logo is uncertain.
- **No on-device verification yet** — user hasn't reported back on whether the halo now fades correctly during carousel scroll.

**Brainstorming task:** Verify the storyboard event="scroll" mechanism reaches non-logo elements. If it does, ship as-is. If it doesn't, look for alternative triggers (e.g., binding halo opacity to a `carousel.scrolling` global state, if such a binding exists).

**Evidence:** `CarouselComponent.cpp:182, 267-268, 799-803`

## 5. Per-system "media type" fallback icons

**What the user wants:** When a game has no thumbnail, instead of showing the game's name as styled text, show a generic icon based on the system's primary physical media type — CD-ROM for disk-based systems (PS1, Saturn, Dreamcast), cartridge for cart systems (N64, NES, SNES), floppy disk for old PCs, etc.

**ES support status:** **Partial.**

- `imageSource` accepts a single value (e.g., `"thumbnail"`); no fallback chain like `"thumbnail,marquee,boxart"`.
- The carousel falls back to text rendering automatically when the configured imageSource isn't available.
- Bindings (`<visible>!exists({game:thumbnail})</visible>`) can conditionally show/hide elements.

**Possible approaches:**

1. **Static overlay per system:**
   - One `<image>` element at the gamecarousel center.
   - Path: `./art/system-media-icons/${system.theme}.png` (per-system file).
   - Visibility: `<visible>!exists({game:thumbnail})</visible>` (only when current game has no thumbnail).
   - Hide the fallback text (`gamecarouselLogoText`) when this overlay is showing.
   - **Pros:** Native theme support; clean per-system mapping.
   - **Cons:** Only ONE icon visible at a time (the selected slot); unselected slots without thumbnails still fall back to text.

2. **Per-logo media icon (would require ES code change):** Modify `CarouselComponent::ensureLogo()` to check for a system-icon fallback before falling back to text. Out of scope for theme-only.

**Art requirements:**

- The TrimUI Brick library has ~178 systems. Not all need unique icons — group by media type:
  - CD-ROM (PS1, Saturn, Dreamcast, NeoGeo CD, PC Engine CD, etc.)
  - Cartridge (NES, SNES, N64, GBA, GB, Genesis, etc.)
  - Floppy disk (Amiga, ST, DOS old PC)
  - Handheld cart (GG, GBC, GBA, etc.)
  - Computer media (cassette, cart, floppy depending on era)
  - "Generic ROM" fallback for arcade/misc.
- Estimated ~5-8 media-type icons covering 90%+ of systems.
- Mapping `system.theme` → media-type icon: a simple lookup table either in the theme (per-system variant files) or via a per-system override.

**Open questions for brainstorming:**

- How many media-type categories?
- Procedurally generated (line-art SVG style, matching the existing flat PSP icon aesthetic)?
- Where does the system-to-media mapping live (one big table in common.xml, or many small per-system include files)?

**Evidence:** `CarouselComponent.cpp:730-767`, `THEMES.md:1242-1246`

## Process notes for v0.10

- These items are roughly independent; can be brainstormed and implemented in any order.
- Items 3 and 5 are related (a fallback icon would solve the halo's text-readability conflict naturally) — consider tackling together.
- Item 4 just needs verification, not a full design pass. Could be confirmed during the first v0.10 deploy.
- Items 1, 2, and 5 each warrant their own brainstorming session.

Recommended order:

1. **First brainstorm:** verify item 4 (halo fade on scroll) — quick win.
2. **Second brainstorm:** items 3 + 5 together (fallback icons + conditional halo).
3. **Third brainstorm:** item 2 (per-logo titles) — feasibility-driven, may end with "accept limitation".
4. **Fourth brainstorm:** item 1 (adaptive layout) — biggest design surface; may need view variants.
