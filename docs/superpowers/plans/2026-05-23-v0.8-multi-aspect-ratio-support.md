# v0.8 Multi-Aspect-Ratio Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `es-theme-xmb-psp` look correct on 4:3, 16:9, 3:2, 1:1, and 8:7 screens without altering existing 4:3 output.

**Architecture:** A normalized layout in `_inc/common.xml` provides 4:3 defaults; four conditional `<include if="${screen.ratio} == X">` directives in `theme.xml` load tiny per-ratio variable-override files (`_inc/aspect-{8x7,3x2,16x9,1x1}.xml`) that redefine only the geometry variables that visually drift on that ratio. ES `formatVersion 7` last-definition-wins gives each ratio its own values; 4:3 inherits the shared defaults unchanged.

**Tech Stack:** ES theme XML (`formatVersion 7`), Knulli `batocera-emulationstation` (pinned commit `9bbb16a`), Docker render harness (`scripts/render.sh`), ImageMagick (`compare -metric AE` for regression).

**Spec:** `docs/superpowers/specs/2026-05-23-v0.8-multi-aspect-ratio-design.md`

**Branch:** `feat/v0.8-aspect-ratios` (already created at commit `6e860be` — verify `git branch --show-current` before starting)

**Library required for gamelist / gamecarousel renders:** `.dev/library/` (already present from harness Task 3; gitignored). If missing, see `docker/README.md` for acquisition steps.

## Task 5: Add 8:7 aspect overrides (smallest delta — start here)

**Files:**
- Create: `_inc/aspect-8x7.xml`
- Modify: `theme.xml` (add one conditional `<include>` after the common.xml include)

8:7 (1.143) is closest to 4:3 (1.333). At 1024×896, the screen is *taller* than 4:3 — most icons need to be slightly less tall in fractional terms to stay square. Per P1 (icon squareness), the relevant overrides target the H dimension of icon variables.

**Suggested starting values** (educated guesses from P1; verify and tune visually):

| Variable | 4:3 default | 8:7 starting value | Reasoning (P1) |
|---|---:|---:|---|
| `sysIconMaxH` | 0.16 | 0.14 | 0.16·768 = 123px; 123/896 ≈ 0.137 → 0.14 |
| `glIconMaxH` | 0.21 | 0.18 | 0.21·768 = 161px; 161/896 ≈ 0.180 |
| `sysCarouselLogoH` | 0.14 | 0.12 | 0.14·768 = 108px; 108/896 ≈ 0.121 |
| `gameCarLogoH` | 0.37 | 0.32 | container-relative; aim for square boxart |

All other variables inherit 4:3 defaults — the cross balance, panel, and video dims need no tuning at 8:7 (very close to 4:3 horizontally).

- [ ] **Step 1: Create `_inc/aspect-8x7.xml`**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!--
  es-theme-xmb-psp - 8:7 aspect-ratio overrides.
  Loaded conditionally by theme.xml when ${screen.ratio} == '8/7'.
  Overrides only the geometry variables that visually drift from
  4:3 defaults at 8:7. Design surface: 1024x896. See P1 in
  docs/superpowers/specs/2026-05-23-v0.8-multi-aspect-ratio-design.md
  for the squareness-in-pixels reasoning behind these values.
  CC-BY-NC-SA 2.0. See CREDITS.md.
-->
<theme>
  <formatVersion>7</formatVersion>
  <variables>
    <!-- Icon squareness (P1): screen is 1024w x 896h, so H fractions
         shrink relative to 4:3 to keep icons square in screen pixels. -->
    <sysIconMaxH>0.14</sysIconMaxH>
    <glIconMaxH>0.18</glIconMaxH>
    <sysCarouselLogoH>0.12</sysCarouselLogoH>
    <gameCarLogoH>0.32</gameCarLogoH>
  </variables>
</theme>
```

| `panelX` | 0.43 | 0.42 | wider screen gives 1 % horizontal breathing room |
| `panelW` | 0.55 | 0.56 | exploit the extra horizontal room |

## Notes for the implementer

**The harness caveat.** The Docker harness renders via desktop GL21 (Mesa software), while a real device renders via GLES2 (programmable shaders). The harness catches XML errors, layout/sizing mistakes, colorset resolution, `<include>` resolution, and storyboard logic reliably. It does **not** guarantee pixel-level colour fidelity, and a few build-specific device quirks may not reproduce. For aspect-ratio work this is fine — layout *is* exactly what the harness verifies well.

**Why P7 (byte-identical 4:3) per task.** Every commit between Tasks 2 and 10 that touches a shared file (common.xml, system.xml, gamelist.xml, theme.xml) re-runs the three 4:3 compares. This catches a leak immediately — if Task N drops a value into the shared scope instead of inside an aspect-N.xml `<variables if=…>` block, the next render will diff non-zero and the implementer can fix before continuing. Cheaper than discovering the regression at Task 11.

**When tuning loops drag on.** If a ratio's visual check (Task N Step 4) takes more than 6 iteration rounds, stop and ask: is the principle still satisfiable with variable nudges, or does the design need to change? Most likely cause: an unmodified shared default (like a font size or wave size) is also drifting and needs to be parameterized too. Add a variable, update the spec, continue.

**When `compare -metric AE` returns non-zero unexpectedly.** Render is non-deterministic in rare cases (font subpixel rendering, video preview frame timing). If you've eyeballed and the diff is in the low single digits AND visually identical, that's acceptable noise — re-render once to confirm, document if persistent. If the diff is hundreds or more, something real changed.
