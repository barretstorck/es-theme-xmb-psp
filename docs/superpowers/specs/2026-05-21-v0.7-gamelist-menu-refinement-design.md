# v0.7 — Gamelist Refinements & ES Menu Re-skin

**Status:** Design approved 2026-05-21. Implementation pending.

**Builds on:** v0.6 (boxart gamecarousel, square cross anchor, larger clock).
v0.6's system carousel, twelve colorsets, wave background/motion, `gamecount`
subset, Roboto Condensed font, the `detailed` text-list gamelist, the
`gamecarousel` boxart gamelist, and the shared right info panel are the
starting point and are otherwise unchanged.

## Goal

Seven refinements to the gamelist views and the EmulationStation menu,
grouped into three areas:

**Gamecarousel layout**
1. **Carousel label styling** — the gamecarousel's per-game name labels (and
   the no-thumbnail text fallback) become white in the system-caption font.
2. **Carousel image size** — the selected game image matches the system icon.
3. **Carousel position** — the selected game sits below the icon, with a hard
   "no game peeks behind the system icon" constraint.

**Right info panel**
4. **Widen the panel** — the shared right info panel expands to fill the space
   to the right of the game column.
5. **Larger description** — the description text font size is increased.

**Wave & menu**
6. **Wave parity** — the animated wave on the gamelist views must render and
   animate identically to the system view.
7. **ES menu re-skin** — the Start-button menu is re-skinned to follow the
   active PSP colorset.

### Context / constraints

- batocera-emulationstation, `formatVersion 7`, Knulli on TrimUI Brick,
  1024x768 (4:3).
- This build has repeatedly diverged from documented behaviour. The ES menu
  re-skin carries the most unknowns — which menu theme element names actually
  affect the menu chrome on this build is not known — so that work opens with
  an on-device discovery spike, the same pattern v0.6 used for the
  gamecarousel.
- All position/size values in this spec are **starting points to be tuned
  on-device** with screenshots. The spec fixes intent and constraints; exact
  numbers are settled during implementation.
- On-device verification only: `scripts/deploy.sh sync` then
  `scripts/ui.sh reload-theme`. Never reboot to reload the UI.

## Changes

### Change 1 — Gamecarousel label styling

The `gamecarousel`'s per-game name labels — shown for every game, and as the
sole content when a game has no scraped `thumbnail` — render in white
(`${textPrimary}`) using RobotoCondensed-Light (`${fontLight}`), matching the
system-name caption.

This also completes the v0.6-deferred "polish the gamecarousel text fallback"
item: a missing-thumbnail game reads as a clean white caption instead of
default carousel text.

The carousel's text-styling property names (e.g. `textColor`,
`selectedTextColor`, `fontPath`, `fontSize`, or equivalents) are confirmed
on-device, since this build has diverged from documented theme schemas before.

**Files:** `_inc/gamelist.xml` (`gamecarousel` element).

### Change 2 — Gamecarousel image size

The **selected** game image is sized to match the gamelist's pinned system
icon (which displays within `maxSize 0.15 0.21`). Unselected neighbours render
slightly smaller, so the column still reads as a carousel with the selection
emphasised — the same selected-is-larger idiom as the system row.

This is achieved by tuning `logoSize` and `logoScale` so that
`logoSize x logoScale` (the selected size) equals the system icon's displayed
size. Exact values are tuned on-device.

**Files:** `_inc/gamelist.xml` (`gamecarousel` element).

### Change 3 — Gamecarousel position and the no-peek constraint

The selected game sits below the system icon. Stacking order top-to-bottom:
system icon, then the `systemName` caption (kept — it provides continuity with
the system view and the shared `detailed` view), then a deliberate padding
gap, then the selected game image.

**Hard constraint — no game peeks behind the system icon.** No part of any
game image may ever be visible peeking out from behind the system icon. A game
is either fully above the icon (in clear space) or fully below it; nothing
renders visibly within the icon's footprint. The system icon's `zIndex` is
raised above the `gamecarousel`'s `zIndex` so the icon always draws over the
carousel. (The system icon is a transparent-background PNG, so raising `zIndex`
alone does not guarantee occlusion — see the mechanism below.)

**Mechanism (settled on-device):**

1. **Primary — straddle spacing.** Tune the carousel's resting-slot spacing
   and `maxLogoCount` so the carousel's resting slots straddle the icon: one
   clear slot above the icon, the selected slot below it, and no resting slot
   within the icon's band. Verify on-device that no game image is visible in
   the icon's footprint in any scroll state.
2. **Fallback — carousel below the icon.** If the straddle layout cannot keep
   games clear of the icon band, position the entire carousel below the icon
   so games never reach the icon's band at all. This still satisfies the
   no-peek constraint; it drops the "carousel extends above the icon"
   behaviour.

The implementation tries mechanism 1 first and falls back to mechanism 2 only
if mechanism 1 cannot hold the constraint on-device. The no-peek constraint is
an explicit verification check, tested across scroll states with screenshots.

**Files:** `_inc/gamelist.xml` (`gamecarousel` element `pos`/`size`/
`logoSize`/`logoScale`/`maxLogoCount`; system icon `logo` `zIndex`).

### Change 4 — Widen the right info panel

The game column (carousel or text list) occupies roughly the left third; its
right edge sits near x≈0.40. The shared right info panel currently lives
around x 0.55–0.95, leaving dead space between the column and the panel and at
the right margin.

The panel is widened to fill from just right of the column (~x0.43) to the
right margin (~x0.98):

- `md_name` (title), `md_rating`, and `md_description` are re-anchored and
  widened to the new horizontal span.
- `md_video` is enlarged proportionally to use the extra width — a larger
  screenshot/preview is the main payoff of the wider panel.
- The top-right clock keeps its position; the panel's top edge stays clear of
  it.

Because this is in the shared `<view name="detailed,gamecarousel">` block, it
applies to both gamelist styles consistently. Exact `pos`/`size` values are
tuned on-device.

**Files:** `_inc/gamelist.xml` (shared `detailed,gamecarousel` block:
`md_name`, `md_rating`, `md_video`, `md_description`).

### Change 5 — Larger description font

`md_description`'s font size increases from `0.022` to approximately `0.028`
for readability. The wider panel (Change 4) gives the larger text the room it
needs. Final size is confirmed on-device.

**Files:** `_inc/gamelist.xml` (shared `detailed,gamecarousel` block:
`md_description`).

### Change 6 — Wave animation parity (gamelist ↔ system)

`_inc/wave-motion.xml` already declares the three animated wave layers
(`waveLayer1/2/3`, `repeat="forever"` storyboards) for the `detailed` and
`gamecarousel` views, not just `system` — yet the gamelist wave is observed to
behave differently from the system view's wave.

This is a discrepancy to **diagnose before changing anything** (root cause
first). The implementation task opens with on-device investigation: capture
the gamelist wave behaviour, compare it against the system view, and identify
*why* they differ. Suspects to rule out: the gamelist views each declare their
own `waveBackground` base image in `_inc/gamelist.xml`, which may layer over or
conflict with the animated layers; storyboard-on-extra behaviour differing
between view types; `zIndex` ordering differences. Once the cause is known,
the fix brings the `detailed` and `gamecarousel` wave to identical rendering
and motion as the `system` view.

Note: the v0.6 known limitation — the system wave resets to t=0 on every
system-carousel navigation — is specific to the `system` view (it has a
carousel to navigate). The gamelist views have no such trigger, so parity
there means a *smoother* continuous wave, not an inherited defect.

**Files:** `_inc/wave-motion.xml`, possibly `_inc/gamelist.xml`
(`waveBackground`).

### Change 7 — ES menu re-skin

The Start-button menu currently renders as ES's stock light chrome — white
rounded panel, grey "MAIN MENU" title, grey selection bar, dark text, grey
footer. The existing `menu.xml` is not reaching that chrome on this build.
The menu is re-skinned to follow the active PSP colorset, in two tasks:

**Task A — menu theming spike.** Probe which ES menu theme elements actually
affect the Start-menu chrome on this Knulli build, screenshotting each probe.
Candidates to test: the panel background (`menuBackground` as a ninepatch with
`path` + `color`, vs. `menuSize`), `menuText` / `menuTextSmall`, `menuTitle`,
`menuFooter`, the selected-row highlight, and `menuSwitch` / `menuSlider` /
`menuButton` inside sub-screens. Output: a documented list of which elements
work, to drive Task B.

**Task B — re-skin from the spike findings.** Theme the menu chrome from the
active colorset: a dark `${waveTint}`-based panel, light `${textPrimary}`
text, `${accent}` / `${selectorGlow}` on the selected row, and themed title
and footer. Switches, sliders, and buttons are themed if the build honours
those elements.

Because the re-skin is driven entirely by the existing colorset variables, all
twelve colorsets re-tint automatically — no colorset file changes. Verified
on-device by spot-checking 2–3 colorsets (e.g. January Blue, August Orange,
September Red) to confirm the menu follows the PSP Color selection.

**Files:** `_inc/menu.xml`; possibly one new ninepatch asset under `art/ui/`
if the panel background needs an image rather than a flat color.

## Out of scope

- No new colorsets; no changes to the twelve existing colorset files (the menu
  re-skin reuses existing colorset variables).
- No changes to the system view layout, the `gamecount` subset, the cross
  anchor values, or the clock.
- The v0.6 known limitation (system-view wave resets on carousel navigation)
  is not addressed; Change 6 only brings the gamelist wave to parity.
- No new gamelist styles; `detailed` and `gamecarousel` are the only two.
