# v0.10 Quick Wins — Design

**Scope:** v0.10.0 release, five user-visible items plus a docs commit.
All items have verified ship-it status in the authenticity audit; this
release ships them as a coordinated bundle with the lowest possible
risk profile.

**Branch strategy:** This spec is authored on
`fix/v0.9.3-battery-syntax-gamecount-spacing`. Per the agreed branch
workflow, the audit + guidelines docs land on `main` first (separate
PR), then a fresh `feat/v0.10` branch is opened off `main` for
implementation.

**PR shape:** One PR off `feat/v0.10` into `main`. Five commits in
dependency order — one per audit item plus a final docs commit:

1. `feat: S6 continuous wave via staticBackground prefix (+ X1 dead-code halo storyboards removed)`
2. `feat: ST1 battery percentage + Battery subset folded (Hide / Glyph / Glyph + Percentage)`
3. `feat: X2 description scroll chevrons (always visible)`
4. `fix: horizontalAlignment → alignment (resolves ~80 parse warnings; visual A/B per element)`
5. `docs: bump README + screenshots for v0.10`

**Verification gate (every commit):**
- Docker render harness pass at all 5 aspect ratios (4:3, 16:9, 3:2, 1:1, 8:7).
- On-device check on the TrimUI Brick (Knulli Scarab, 4:3, 1024×768).
- Item 4 (typo fix) additionally requires a per-element visual A/B against v0.9.3 — see Item 4 details below.

**Audit cross-references:** S6, X1, ST1, X2, plus the
`horizontalAlignment` typo noted in the audit's `Cross-cutting
constraints` section. See [`docs/psp-authenticity-audit.md`](../../psp-authenticity-audit.md).

## Item 1 — S6 continuous wave + X1 dead-code cleanup

**Goal:** Wave animation persists continuously across system carousel
navigation. Today the storyboard restarts at t=0 on every cursor
change because the wave layers are declared as `extra="true"` images
that go through ES's per-system `backgroundExtras` lifecycle (which
calls `extra->onShow()` → `mStoryboardAnimator->reset()` on cursor
change).

**Mechanism:** Knulli ES has an undocumented separate render path for
elements whose `name` attribute starts with the literal string
`"staticBackground"` (`SystemView::getViewElements`,
`SystemView.cpp:1045-1065`). These go through `mStaticBackgrounds`,
which is loaded once at view construction and ticks every frame
regardless of cursor change — `onShow()` is only called on view-show,
not cursor change, so the storyboard `reset()` cascade never fires.

### Files touched

- `_inc/system.xml`
- `_inc/wave-motion.xml`
- `README.md`

### Changes to `_inc/system.xml`

| Element (current) | Element (after) |
|:---|:---|
| `<image name="waveBackground" extra="true">` | `<image name="staticBackgroundWave">` (no `extra`) |
| (waveLayer1/2/3 inherited from `wave-motion.xml`) | Inline `staticBackgroundLayer1/2/3` declarations (no `extra`) — copy the storyboard XML verbatim from `wave-motion.xml` |
| `<image name="selectedHalo" extra="true">` with two `<storyboard>` blocks | `<image name="staticBackgroundHalo">` (no `extra`), both `<storyboard>` blocks deleted, `<zIndex>` bumped 3 → 10 |

**zIndex rationale.** At `zIndex=10` the halo renders above all
`staticBackground*` wave elements (zIndex 0/1/2/3) but below the
carousel (zIndex 5/6). Without this bump, the wave layers paint over
the halo in the new `mStaticBackgrounds` render path order. The exact
load order was verified during the spike at
`SystemView.cpp:889` (the `mStaticBackgrounds` render loop).

**Why delete both halo storyboards.** The pre-existing
`<storyboard event="scroll">` on the halo is dead code on this build
— `CarouselComponent` fires the `scroll` event only on its own
intrinsic logos via `mLogo[i]->selectStoryboard("scroll")`, never on
extras (`CarouselComponent.cpp:267, 652`). The default storyboard
(opacity 0 → 1 over 220ms) fired once at initial view-show, fine but
unnecessary; deleting it simplifies the rename pass.

### Changes to `_inc/wave-motion.xml`

Change `<view name="system,detailed,gamecarousel">` to
`<view name="detailed,gamecarousel">`. The system view now has its
wave layers inline rather than included. Gamelist views are unaffected
by U6 / S6 (the cursor-reset behavior is system-view-specific) — they
keep their existing motion include.

### Changes to `README.md`

Delete the bullet "Wave animation resets on every system carousel
navigation..." from the `Known limitations` section. Other limitations
remain.

### Verification

1. **Docker harness, all 5 aspect ratios:** Render system view.
   Visual inspection: wave + halo behave identically to v0.9.3 in the
   single-frame steady state. Halo brightness should be marginally
   higher than v0.9.3 because the new ordering removes the
   waveLayer3 / halo zIndex collision the spike documented.
2. **On-device, TrimUI Brick:** Navigate left-right repeatedly through
   8-10 systems. Wave animation should not visually reset between
   transitions. This is the load-bearing acceptance test — the spike
   verified the mechanism on the harness using GL21 software
   rendering, while the device uses GLES2.

### Risk and contingency

If on-device behavior diverges from the Docker harness — e.g., the
`mStaticBackgrounds` render path behaves differently on GLES2 —
fall back to v0.9.3 wave declarations and reopen the audit's S6
entry with the on-device findings. No partial deployment: this
commit is atomic.

## Item 2 — ST1 battery percentage + Battery subset fold

**Goal:** Add numeric battery percentage to the status bar next to the
existing glyph, controlled by a folded Battery subset offering three
values: `Hide`, `Glyph`, `Glyph + Percentage`.

**Design choice (settled in brainstorming):** Use a binding-based
`<text>` element with `<value>{global:batteryLevel}%</value>` and
`<visible>{global:battery}</visible>`. The percentage shows whenever
the device reports a battery, independent of ES's `ShowBattery` user
setting. User control over icon vs. icon+text is provided by the
theme's own subset rather than ES's preference. Most PSP-faithful;
matches PSP's combined battery widget appearance.

### Files touched

- `theme.xml` (subset block restructured)
- `_inc/common.xml` (no structural change; `<batteryIcon>` block stays)
- `_inc/battery-show.xml` → renamed to `_inc/battery-glyph.xml` (content unchanged)
- `_inc/battery-hide.xml` (content unchanged — clock-shift math preserved)
- `_inc/battery-glyph-pct.xml` (NEW)

### Subset block in `theme.xml`

```xml
<subset name="battery" displayName="Battery">
  <include name="Glyph + Percentage">./_inc/battery-glyph-pct.xml</include>
  <include name="Glyph">./_inc/battery-glyph.xml</include>
  <include name="Hide">./_inc/battery-hide.xml</include>
</subset>
```

`Glyph + Percentage` is listed first to be ES's default when no user
selection exists. Verify on first implementation that ES does pick the
first entry as default — if not, add a `default="..."` attribute or
similar mechanism.

### New `_inc/battery-glyph-pct.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<theme>
  <formatVersion>7</formatVersion>

  <!-- Glyph + Percentage subset: existing batteryIcon (from common.xml)
       stays at pos.x=0.94. Add a binding-based <text> for the numeric
       percentage immediately to its left. Both render whenever the
       device reports a battery. Shifts the clock leftward to avoid
       overlap with the percentage element. -->

  <view name="screen">
    <!-- Numeric percentage to the LEFT of the battery glyph.
         Right-aligned so the % sits flush against the glyph's left edge. -->
    <text name="batteryPercent" extra="true">
      <pos>0.88 0.03</pos>
      <size>0.05 0.06</size>
      <fontPath>${fontRegular}</fontPath>
      <fontSize>0.030</fontSize>
      <color>${textPrimary}</color>
      <alignment>right</alignment>
      <value>{global:batteryLevel}%</value>
      <visible>{global:battery}</visible>
    </text>

    <!-- Clock shifted left so its right edge clears the percentage's
         left edge. v0.9.3 clock pos.x=0.78 right-edge at 0.92 collides
         with the new percentage's left edge at 0.88. Shifting clock
         to pos.x=0.72 puts its right edge at 0.86 — 0.02 gap to the
         percentage element. -->
    <text name="clock">
      <pos>0.72 0.03</pos>
      <size>0.14 0.06</size>
      <fontPath>${fontRegular}</fontPath>
      <fontSize>0.042</fontSize>
      <color>${textPrimary}</color>
      <alignment>right</alignment>
    </text>
  </view>
</theme>
```

### `_inc/battery-glyph.xml` (renamed from `battery-show.xml`)

Content identical to v0.9.3's `battery-show.xml`. Pure rename.

### `_inc/battery-hide.xml`

Unchanged from v0.9.3. The clock-right-shift math is preserved.

### Verification

1. **Docker harness, no battery present.** Render screen view with each
   subset value:
   - `Hide`: clock at right edge, no battery widget. Identical to
     v0.9.3 `Hide`.
   - `Glyph`: clock at v0.9.3 position, battery slot reserved but
     empty (harness reports no battery). Identical to v0.9.3 `Show`.
   - `Glyph + Percentage`: same visual as `Glyph` in the harness —
     `<visible>{global:battery}</visible>` is false so the percentage
     `<text>` doesn't render; clock is at the shifted-left position
     but visually indistinguishable from v0.9.3 `Show` in the harness
     because there's no battery for the slot.
2. **On-device on TrimUI Brick (has a battery).** Verify:
   - `Glyph`: glyph shown, no percentage. Visually identical to
     v0.9.3 `Show`.
   - `Glyph + Percentage`: glyph + numeric percentage both shown,
     percentage immediately left of glyph, clock shifted left so the
     three elements are spaced cleanly across the top-right cluster.
   - `Hide`: clock at the right edge, no battery widget. Identical to
     v0.9.3 `Hide`.

### Migration note (for the v0.10 changelog)

Users with `Battery: Show` set in their `es_settings.cfg` will, on
first launch of v0.10, find that subset value is gone — ES picks the
new default (`Glyph + Percentage`). Document this in the release
notes:

> **Battery subset changed.** v0.9.3's `Battery: Show / Hide` is
> replaced by `Battery: Glyph + Percentage / Glyph / Hide`. Users
> who had `Show` will get the new default `Glyph + Percentage`; if
> you prefer the icon-only look, pick `Glyph`.

### Risk

If `{global:batteryLevel}` doesn't update during a render — i.e., if
the binding is read once at theme-load rather than per-frame — the
percentage will be stale until next ES restart. The
spike's binding probe confirmed it resolves correctly but didn't test
update frequency. Acceptance criterion: leave the device running for
30+ minutes with a discharging battery; the percentage should track
the glyph's state changes.

## Item 3 — X2 description scroll chevrons

**Goal:** Two static chevron glyphs (▲ at top, ▼ at bottom) on the
gamelist description container to indicate scroll affordance. Always
visible; the audit explicitly accepts the slight overhang on short
descriptions as the tradeoff for not having a description-overflow
binding.

### Files touched

- `_inc/gamelist.xml` (add two `<image>` elements to the shared `detailed,gamecarousel` view block)
- `_inc/common.xml` (add `descScrollDownY` variable)
- `_inc/aspect-1x1.xml` (override `descScrollDownY` for the 1:1 layout where description height differs)
- `art/ui/chevron-up.png` (NEW)
- `art/ui/chevron-down.png` (NEW)
- `scripts/gen-chevrons.py` (NEW)

### `scripts/gen-chevrons.py`

Pattern matches the existing `scripts/gen-halo.py` and
`scripts/gen-battery-icons.py`. Generates two 32×24 PNGs with a white
isoceles triangle on transparent canvas. The up-chevron has its apex
at the top center (y=4, x=16); the down-chevron has its apex at the
bottom center (y=20, x=16). 4-pixel padding on all sides ensures no
edge clipping after upscaling.

```python
# Sketch — fill in via PIL or equivalent
from PIL import Image, ImageDraw

def make_chevron(direction: str, out_path: str):
    img = Image.new("RGBA", (32, 24), (0, 0, 0, 0))
    draw = ImageDraw.Draw(img)
    if direction == "up":
        # apex at top, base at bottom
        draw.polygon([(16, 4), (4, 20), (28, 20)], fill=(255, 255, 255, 255))
    else:  # down
        # apex at bottom, base at top
        draw.polygon([(16, 20), (4, 4), (28, 4)], fill=(255, 255, 255, 255))
    img.save(out_path, "PNG")

make_chevron("up", "art/ui/chevron-up.png")
make_chevron("down", "art/ui/chevron-down.png")
```

### Changes to `_inc/common.xml`

Add to `<variables>`:

```xml
<descScrollDownY>0.91</descScrollDownY>
```

This is the y-coordinate for the down-chevron at 4:3 default. Equal to
`panelDescY + panelDescH` minus a small margin (`0.60 + 0.32 - 0.01 = 0.91`).

### Changes to `_inc/aspect-1x1.xml`

Add (or modify existing) variable override:

```xml
<descScrollDownY>0.93</descScrollDownY>
```

(at 1:1, `panelDescY=0.58, panelDescH=0.36`, so down-chevron sits at
`0.58 + 0.36 - 0.01 = 0.93`).

Other aspect ratios (3:2, 16:9, 8:7) use 0.91 from common.xml; their
`panelDescY` and `panelDescH` match the 4:3 default. No override
needed.

### Changes to `_inc/gamelist.xml`

Insert into the `<view name="detailed,gamecarousel">` block, after the
existing `md_description` element:

```xml
<!-- Description scroll affordance: ▲ pinned at description top edge,
     ▼ pinned at description bottom edge. Always visible; no overflow
     binding exists (audit X2). -->
<image name="descScrollUp" extra="true">
  <path>./art/ui/chevron-up.png</path>
  <pos>${panelX} ${panelDescY}</pos>
  <origin>0 1</origin>
  <maxSize>0.014 0.011</maxSize>
  <color>${textSecondary}</color>
  <zIndex>6</zIndex>
</image>

<image name="descScrollDown" extra="true">
  <path>./art/ui/chevron-down.png</path>
  <pos>${panelX} ${descScrollDownY}</pos>
  <origin>0 0</origin>
  <maxSize>0.014 0.011</maxSize>
  <color>${textSecondary}</color>
  <zIndex>6</zIndex>
</image>
```

`origin 0 1` on the up-chevron means its anchor is bottom-left of the
glyph — so `pos.y = panelDescY` places the chevron's bottom edge at
the description's top edge, with the chevron sitting just above.
`origin 0 0` on the down-chevron places its top-left at the anchor,
so the glyph sits just below the description's bottom edge.

`<color>${textSecondary}` tints the white glyph to the colorset's
secondary text color, matching the description text's lower-contrast
role.

### Verification

1. **Docker harness, all 5 aspect ratios.** Render `detailed` and
   `gamecarousel` views. Confirm chevrons appear at top and bottom
   of the description box, sized and positioned correctly. At 1:1,
   verify the per-aspect `descScrollDownY` override puts the down-
   chevron at the right place.
2. **On-device on TrimUI Brick.** Spot check: navigate to a game with
   a long description. Chevrons should be visible at top and bottom
   of the description text in both gamelist styles.

### Risk

If the chevrons look too prominent on a short description (overhang
issue), the fallback is to drop the up-chevron and keep only the
down-chevron — text usually scrolls downward, so a single bottom
chevron is the most useful affordance. Decision deferred until visual
review of the v0.10 candidate.

## Item 4 — `horizontalAlignment` → `alignment` typo fix

**Goal:** Replace the (silently-ignored) `<horizontalAlignment>` XML
property with the correct `<alignment>` everywhere it appears in the
theme. Resolves the ~80 `Unknown property : text.horizontalAlignment`
parse warnings per render that the spike documented.

### Pre-implementation step (mandatory)

Build a per-element audit table before changing any XML:

```bash
grep -rn "horizontalAlignment" _inc/ colors/ theme.xml > .dev/typo-audit.txt
```

For each occurrence, record:
- `file:line`
- The owning element (`<text name="X">` / `<systemInfo>` / etc.)
- The current value (`right`, `center`, `left`)
- ES's default alignment for that element type (look up in source)

### Per-element resolution

For each occurrence in the audit table:

1. Render v0.9.3 + v0.10-candidate side-by-side via Docker at 4:3.
2. Compare pixel diff in the element's bounding box.
3. **No visible diff** → fix lands as-is (the intended `<alignment>`
   value already matches ES's default).
4. **Visible diff** → judgement call:
   - **Default (option 1):** keep the corrected `<alignment>` value.
     The theme XML clearly intended that alignment; the corrected
     version is what was meant.
   - **Fallback (option 2):** override `<alignment>X</alignment>` to
     whatever ES was defaulting to. Preserves v0.9.3's rendering
     exactly; only used if the corrected alignment is visually wrong.

### Files touched

Determined by the grep at implementation time. Likely candidates
based on the audit's mention:
- `_inc/common.xml` (clock element at minimum)
- `_inc/system.xml` (systemInfo, systemName)
- `_inc/gamelist.xml` (md_name, md_description)
- Per-aspect-ratio overrides (`_inc/aspect-*.xml`)

### Commit shape

Single commit `fix: horizontalAlignment → alignment (resolves ~80 parse warnings)`.

Commit message body lists every changed element + the before/after
alignment decision (option 1 default or option 2 override).

### Verification

1. **Parse log:** Docker harness render produces zero
   `Unknown property : text.horizontalAlignment` warnings.
2. **Per-element A/B:** the audit table from the pre-implementation
   step shows either "no visible diff" or "diff resolved via option-2
   override".
3. **On-device on TrimUI Brick:** spot check the system view and both
   gamelist views for any visible regression vs. v0.9.3.

### Scope contingency

If the per-element audit reveals more than ~10 elements with visible
diffs needing option-2 overrides, escalate to a separate spec.
Cap v0.10's typo fix to "drop-in safe" elements only; defer the
visually-meaningful ones to a follow-up iteration. This keeps v0.10's
risk profile small.

## Acceptance criteria for the v0.10 PR

The PR is mergeable when:

1. All five commits build and parse cleanly (no new ES warnings
   beyond what's been baseline-accepted in v0.9.3).
2. Docker render harness passes for all 5 aspect ratios on every
   commit individually (not just the final state).
3. On-device TrimUI Brick check:
   - System view: continuous wave across navigation (S6 acceptance).
   - Status bar: battery percentage visible when `Battery: Glyph +
     Percentage` is set; clock shifted left to clear (ST1).
   - Gamelist views: chevrons present at description top + bottom (X2).
   - No visual regressions in `detailed` or `gamecarousel` rendering
     relative to v0.9.3 (typo-fix Item 4 only).
4. Parse log shows zero `Unknown property : text.horizontalAlignment`
   warnings (Item 4 verification).
5. README and screenshots reflect the v0.10 state.

If any of the above fails on-device after a Docker pass, the relevant
commit gets backed out — the PR does not merge until all five items
clear both gates.
