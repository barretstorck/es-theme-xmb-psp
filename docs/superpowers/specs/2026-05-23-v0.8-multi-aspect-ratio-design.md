# v0.8 — Multi-aspect-ratio support — design spec

**Status:** approved
**Date:** 2026-05-23
**Predecessor:** v0.7 (gamelist/menu refinements + ES menu re-skin)

## Goal

Make `es-theme-xmb-psp` look correct on the five common Knulli/Batocera handheld
display aspect ratios — **4:3, 16:9, 3:2, 1:1, 8:7** — without breaking the
existing 4:3 TrimUI Brick experience. Today the README warns "Other aspect
ratios will letterbox or stretch"; v0.8 retires that caveat for the listed
ratios.

## Background

`batocera-emulationstation` (Knulli build, commit `9bbb16a`) supports
per-element and per-include **conditional XML** via the `if=` attribute,
evaluated against bindings exposed by `BindingManager` and parsed by
`ThemeData::parseFilterAttributes`. Relevant bindings:

- `${screen.ratio}` — a string like `"4/3"`, `"16/9"`, `"3/2"`, `"1/1"`, `"8/7"`.
  Implemented by `Renderer::getAspectRatio()` which nearest-matches the actual
  screen proportion against a built-in table.
- `${screen.width}`, `${screen.height}` — pixel dimensions.
- `${screen.vertical}` — boolean.

Confirmed by reading `/opt/es/es-core/src/ThemeData.cpp` and `THEMES.md` inside
the harness image during the exploration phase. `THEMES.md` line 481 documents
the exact pattern: `<image if="${screen.ratio} == '16/9'">`.

The theme's coordinate system is already CSS-vw/vh-equivalent — `<pos>0.24 0.291</pos>`
is "24 % of screen width, 29.1 % of screen height". What breaks on non-4:3 isn't
the unit system; it's that **percentage-of-width and percentage-of-height stop
being equal pixels when the aspect changes**, so anything visually tuned to "look
square" or "match the icon" drifts.

## Architecture

A normalized layout (4:3 values, identical to today) lives in `_inc/common.xml`.
Four new conditional includes — one per non-4:3 ratio — load *after*
`common.xml` and redefine only the variables that drift on that ratio. The view
files (`system.xml`, `gamelist.xml`, `menu.xml`, `wave-motion.xml`) consume the
variables and don't carry any per-ratio knowledge.

Because ES `formatVersion 7` resolves `${var}` at element-parse time and the
include order is `common → aspect-override → views`, last-definition-wins gives
each ratio its own values without altering 4:3. This is the same mechanism
colorsets already use — established and tested (v0.7 colorset-clobber bug fix
confirmed last-definition-wins works correctly on this build).

The conditional dispatch lives in `theme.xml`:

```xml
<include>./_inc/common.xml</include>
<include if="${screen.ratio} == '16/9'">./_inc/aspect-16x9.xml</include>
<include if="${screen.ratio} == '3/2'">./_inc/aspect-3x2.xml</include>
<include if="${screen.ratio} == '1/1'">./_inc/aspect-1x1.xml</include>
<include if="${screen.ratio} == '8/7'">./_inc/aspect-8x7.xml</include>
<subset name="colorset">…</subset>
<include>./_inc/system.xml</include>
<include>./_inc/gamelist.xml</include>
<include>./_inc/menu.xml</include>
<include>./_inc/wave-motion.xml</include>
<subset name="gamecount">…</subset>
```

ES picks at most one aspect include (or none for 4:3 / unknown). Unknown ratios
silently inherit the 4:3 defaults — same "letterbox or stretch" outcome we ship
today, explicitly preserved.

## Parameterized variables

`_inc/common.xml` already declares colour, font, sound, and XMB cross anchor
variables. We extend that block with ~18 new geometry variables — every literal
in the view files that visually drifts with aspect graduates into a named
variable. Aspect-neutral literals (font sizes, wave-layer sizes, corner-anchored
helpsystem/clock positions) stay as literals.

### Existing (kept, default values unchanged)

### View-file usage example

```xml

<image name="logo">
  <maxSize>0.12 0.16</maxSize>
  …
</image>

<!-- after (variable) -->
<image name="logo">
  <maxSize>${sysIconMaxW} ${sysIconMaxH}</maxSize>
  …
</image>
```

### Per-ratio churn estimate

| Ratio | Approx. variables overridden | Notes |
|------:|------:|---|
| 4:3   | 0 (defaults)             | shared default — no override file |
| 8:7   | 2–3                      | very close to 4:3; expect mostly identical |
| 3:2   | 5–8                      | wider — icon dims + panel widths |
| 16:9  | 8–12                     | much wider — cross balance + panel + carousel |
| 1:1   | 10–14                    | square — cross is the hardest case, vertical arm has less room |

Concrete numeric values per ratio are **not** in this spec — they're discovered
during implementation by rendering each ratio in the harness and adjusting.
The spec fixes the *principles* (next section) and the *variables to tune*;
the implementation plan fixes the *per-ratio numbers* via render-and-adjust.

## Per-ratio tuning principles

These rules drive the implementer's per-ratio override choices.

**P1. Icon squareness.** System icons (system view, gamelist view) and boxart
logos should appear roughly square in *screen pixels* — not 0.15w × 0.21h
fractions. For each ratio, compute the screen pixel aspect, then choose
`sysIconMaxW/H`, `glIconMaxW/H`, `sysCarouselLogoW/H`, and `gameCarLogoW/H` such
that `W·screen_w ≈ H·screen_h`. Exception: source PNGs that aren't square keep
their source aspect via `<maxSize>` semantics (ES preserves image aspect within
the bounding box).

**P2. XMB cross visual balance.** The PSP cross should look cross-shaped, not
T-shaped or L-shaped. The horizontal arm spans the screen width minus the icon
column; the vertical arm spans `gameColH` of screen height. Tuning rule: pick
`crossX`, `gameColX`, and `gameColW` so the icon column reads as the visual
center of the vertical arm, and so the right info panel doesn't pinch it. On
square (1:1) the cross is the hardest case — accept that `crossX` may shift
further left (e.g. ~0.20) to give the panel more room.

**P3. Info panel fits.** `panelX` and `panelW` are sized so
`panelX + panelW ≤ 0.98` (small right margin for the clock) and
`panelX ≥ gameColX + gameColW + 0.03` (gap between vertical arm and panel). On
1:1, the panel must be narrower than on 16:9; on 8:7, slightly wider than on
4:3.

**P4. Video preserves 4:3 scraper aspect.** Most Knulli scraper screenshots are
4:3. `md_video`'s bounding box (`mdVideoW × mdVideoH`) should produce a 4:3
area in *screen pixels*: `(mdVideoW·screen_w) / (mdVideoH·screen_h) ≈ 4/3`. ES
preserves video aspect inside the box, so a non-4:3 box just adds letterbox bars
— undesirable.

**P5. Wave background is untouched.** The wave layer PNGs and their `<size>`
values are aspect-neutral (seamless horizontal tile, gradient vertical fade).
Confirmed by inspection during exploration; no override needed for any ratio.

**P6. Corner-anchored chrome is untouched.** Helpsystem (`0.02 0.94`,
bottom-left) and clock (`0.84 0.03`, top-right) stay where they are on every
ratio. Font sizes are screen-height-relative and remain readable.

**P7. 4:3 visual output is byte-identical before and after.** Variables for
which the 4:3 value matches the previous literal stay identical. The
implementer verifies by rendering 4:3 *before* any view-file edits, saving
those as `before-*.png`, and re-rendering after each task. The post-task
renders must match `before-*.png` pixel-for-pixel
(`compare -metric AE before.png after.png null:` returns 0). This is the
no-regression gate for existing TrimUI Brick users.

**P8. Unknown ratios fall back to 4:3 defaults.** If `${screen.ratio}` returns
something not in our list (e.g. `21/9`, `5/4`, `9/16` vertical), none of the
four conditional `<include>`s fire and the device gets the shared 4:3 layout.
Same "letterbox or stretch" outcome we ship today — explicitly preserved.

## Verification (harness usage)

The Docker harness already takes `--resolution WxH`, so the per-ratio test loop
is render commands per view. The implementer renders the relevant view at the
canonical resolution for each ratio, eyeballs against the principles, and
iterates override values.

### Render matrix (per task, after each override change)

| Ratio | Resolution | system | detailed | gamecarousel | menu |
|-------|-----------:|:------:|:--------:|:------------:|:----:|
| 4:3   | 1024×768   | ✓ (P7 gate) | ✓ (P7 gate) | ✓ (P7 gate) | — |
| 16:9  | 1280×720   | ✓ | ✓ | ✓ | ✓ once |
| 3:2   | 720×480    | ✓ | ✓ | ✓ | ✓ once |
| 1:1   | 720×720    | ✓ | ✓ | ✓ | ✓ once |
| 8:7   | 1024×896   | ✓ | ✓ | ✓ | ✓ once |

5 ratios × 3 views = 15 view renders per iteration, plus one menu render per
non-4:3 ratio for regression spot-check.

### Example commands

```
./scripts/render.sh --view system       --resolution 1280x720 --out .dev/sys-16x9.png
./scripts/render.sh --view gamecarousel --resolution 720x720  --library .dev/library --out .dev/gcar-1x1.png
./scripts/render.sh --view menu         --resolution 1280x720 --out .dev/menu-16x9.png
```

### 4:3 regression gate (P7) procedure

Before starting any view-file edits:

```
./scripts/render.sh --view system       --resolution 1024x768 --out .dev/before-sys.png
./scripts/render.sh --view detailed     --resolution 1024x768 --library .dev/library --out .dev/before-detailed.png
./scripts/render.sh --view gamecarousel --resolution 1024x768 --library .dev/library --out .dev/before-gcar.png
```

After each task that touches the variable promotion or override files:

```
./scripts/render.sh --view system       --resolution 1024x768 --out .dev/after-sys.png
compare -metric AE .dev/before-sys.png .dev/after-sys.png null:    # must print 0
```

Any non-zero diff means a 4:3-value override leaked into the shared layout. Fix
and re-run.

## Scope

### In scope

- `_inc/aspect-{16x9,3x2,1x1,8x7}.xml` + conditional includes in `theme.xml`.
- Variable promotion in `_inc/common.xml`, `_inc/system.xml`, `_inc/gamelist.xml`.
- Per-ratio tuning of `crossX/Y`, icon dims, vertical-arm dims, right-panel
  dims, video dims — system + detailed + gamecarousel views.
- Five system-view screenshots in `docs/screenshots/`.
- README Compatibility section update.
- 4:3 byte-identical regression gate per task (P7).

### Out of scope (deferred)

- **Vertical (portrait) screens.** ES detects `screen.vertical == true`; we
  don't override. Existing layout is landscape-only by design.
- **21:9 ultrawide, 5:4, 32:9, exotic ratios.** Silently fall back to 4:3
  defaults (P8). README notes "other ratios fall back to the 4:3 layout — may
  letterbox or stretch."
- **Smaller-than-handheld screens** (`tinyScreen=true`, RPi-style 320×240). Not
  targeted by this theme.
- **Per-ratio colorsets, per-ratio art assets, per-ratio fonts.** Only geometry
  varies by ratio; colour, art, and fonts stay shared.
- **Per-ratio menu re-tuning.** Menu is ES chrome that we colour-theme only;
  layout is ES's, not ours.
- **Re-generating wave PNGs at different aspect ratios.** Confirmed
  aspect-neutral by inspection (P5).

## Backward compatibility

P7 (byte-identical 4:3) is the explicit gate. Existing TrimUI Brick installs
see zero visual change after upgrading to v0.8. Users on other ratios go from
"letterbox or stretch" to tuned layouts. Users on unsupported ratios stay on
the 4:3 fallback — no regression vs v0.7.
